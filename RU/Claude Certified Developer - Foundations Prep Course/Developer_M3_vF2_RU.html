«Сборка» в этом модуле

Всё в этом модуле построено вокруг одной повторяющейся проблемы: код, который работает на вашей машине, в вашей сессии или в тестовой среде, теперь должен выдержать запуск кем-то другим — в продакшене, на реальных системах компании. На вашей машине режим разрешений казался безопасным, правила проекта были достаточно короткими, чтобы их соблюдать, навык находил нужный скрипт, учётные данные лежали прямо в конфигурационном файле, а подключение работало в тестовой среде. В тот момент, когда работа покидает вашу машину, каждое из этих удобств может превратиться в сбой: режим разрешений удаляет файл, который никогда не должен был попадать в область действия, одно правило теряется среди сотен строк, навык указывает на путь, которого нет ни на одной другой машине, закоммиченный ключ утекает в течение нескольких часов, а шаг конфигурации, актуальный только для тестовой среды, обрушивает продакшен-подключение. Работа в этом модуле — научиться понимать, какое решение по конфигурации предотвращает какой из этих сбоев, прежде чем они проявятся перед коллегой или аудитором.

Цикл агента Claude Code, режимы разрешений, настройки и место точки контроля человеком

Модуль 2 установил, как цикл агента работает на уровне API: модель вызывает инструменты, получает результаты обратно и продолжает, пока задача не будет выполнена.

Claude Code выполняет тот же цикл в терминале, но добавляет ещё один уровень: систему разрешений, которая контролирует каждое действие, которое агент хочет выполнить. Прежде чем что-либо настраивать, нужно понять, как работает цикл и что контролируют режимы разрешений.

Как Claude Code работает над задачей: исследование, план и код

Когда вы даёте Claude Code задачу, он не начинает писать код немедленно. Сначала он читает файлы, прослеживает соответствующую логику и формирует представление о кодовой базе — это фаза исследования. Затем, когда понимания достаточно, чтобы предложить изменение, он создаёт план. План — это структурированное описание изменений, которые он намерен внести. Только после того как вы просмотрите и одобрите план, он переходит к фазе написания кода, где вносит и выполняет изменения.

Эта последовательность важна по двум причинам. Во-первых, она даёт лучший результат: Claude Code понимает кодовую базу, прежде чем что-либо трогать, поэтому делает меньше допущений и замечает больше побочных эффектов. Во-вторых, именно здесь подключаются режимы разрешений: режим plan удерживает Claude Code на фазе исследования, блокируя все правки файлов и команды оболочки, пока вы его не освободите, что делает его полезным вариантом по умолчанию для незнакомых кодовых баз или ответственной работы.

Режимы разрешений: подтверждения, точки контроля и ограничения

Режимы разрешений контролируют, как часто Claude Code останавливается, чтобы запросить подтверждение. Каждый режим предполагает свой компромисс между скоростью и контролем. Правильный выбор зависит от того, насколько хорошо вы знаете кодовую базу и насколько обратимы изменения.

Выберите каждую вкладку, чтобы узнать, что этот режим одобряет автоматически, что всё ещё требует подтверждения, и его ограничения.

Что одобряется автоматически: Только чтение. Запрашивает подтверждение почти перед каждой правкой или командой.

Что всё ещё требует подтверждения: Все правки файлов и команды оболочки требуют подтверждения.

Ограничения: Безопасно, но медленно для доверенной работы. Базовый вариант для любого нового проекта или незнакомой кодовой базы.

Что одобряется автоматически: Чтение, правки файлов и распространённые команды файловой системы (mkdir, touch, rm, rmdir, mv, cp и sed) внутри рабочего каталога. Автоодобрение ограничено путями внутри рабочего каталога, защищённые пути по-прежнему запрашивают подтверждение.

Что всё ещё требует подтверждения: Все остальные команды оболочки; записи вне рабочего каталога; записи в защищённые пути.

Ограничения: Доверенная локальная работа, где выполнение команд оболочки всё ещё требует контроля человека. Не подходит, если агенту нужно запускать скрипты.

Что одобряется автоматически: Только чтение. Исследует и предлагает; не вносит изменений.

Что всё ещё требует подтверждения: Все правки файлов и команды оболочки, пока вы не одобрите план.

Ограничения: Исследование и планирование на чувствительных или незнакомых кодовых базах. Не подходит для задач, которые должны записывать результат.

Что одобряется автоматически: Всё, но отдельный классификатор сначала проверяет каждое действие и блокирует всё, что выходит за рамки вашего запроса, нацелено на нераспознанную инфраструктуру или выглядит вызванным враждебным либо неуместным содержимым.

Что всё ещё требует подтверждения: Развёртывания и миграции в продакшн, массовое удаление, эксфильтрация учётных данных и принудительный push в main блокируются по умолчанию.

Ограничения: Сокращает число запросов, но не гарантирует безопасность; это исследовательская предварительная версия, а не замена проверке чувствительных операций. Доступность зависит от тарифного плана, версии модели и настроек администратора. Всегда проверяйте актуальные требования перед сборкой.

Что одобряется автоматически: Только инструменты, предварительно одобренные вами в правиле allow, плюс команды только для чтения. Автоматически ОТКЛОНЯЕТ всё остальное.

Что всё ещё требует подтверждения: Каждый вызов инструмента, не входящий в список разрешённых, отклоняется. Очереди на подтверждение нет.

Ограничения: Создан для закрытых CI-сред и скриптов. Хорошо ограничивает, но не является способом снизить трение в локальной интерактивной работе.

Что одобряется автоматически: Все вызовы инструментов. Без запросов на подтверждение и без проверок безопасности.

Что всё ещё требует подтверждения: Ничего в обычной работе. Стандартные проверки разрешений обходятся; только катастрофические команды удаления, такие как rm -rf / и rm -rf ~, всё ещё вызывают запрос в качестве крайней меры.

Ограничения: Только внутри изолированного контейнера или ВМ, где среда одноразовая. Никогда — на рабочей станции разработчика против живой кодовой базы.

Где хранится конфигурация и на кого она распространяется

Настройки можно размещать на нескольких уровнях, и каждый уровень определяет область действия содержащихся в нём правил.

  • Уровень пользователя (~/.claude/settings.json): Применяется ко всем проектам на машине. Правильное место для предпочтений, которые должны следовать за вами повсюду, например предпочитаемый режим по умолчанию для исследовательской работы.
  • Уровень проекта (.claude/settings.json, закоммичен в репозиторий): Применяется ко всем, кто клонирует репозиторий. Правильное место для общекомандных соглашений, правил allow для инструментов, используемых в проекте, и правил deny для путей, которые не следует трогать.
  • Локальный уровень проекта (.claude/settings.local.json): Персональные переопределения для одного проекта, автоматически игнорируемые git. Правильное место для ваших личных предпочтений, которые не должны попадать в общий репозиторий команды.
  • Корпоративный уровень (managed-settings.json, задаётся администраторами): Не может быть переопределён пользователями или файлами проекта. Правильное место для общеорганизационных мер безопасности, таких как запрет правок файлов окружения или блокировка определённых команд оболочки во всех проектах.

Правила allow и deny накладываются поверх выбранного режима. Правило deny всегда побеждает правило allow, независимо от действующего режима. Самый устойчивый механизм управления — это правило deny на корпоративном уровне: его не может убрать ни один отдельный разработчик, и оно действует даже при установленном режиме обхода.

Где человеку всё ещё нужно смотреть: размещение точки контроля по цене худшего сценария

Режимы разрешений и правила deny определяют, что агент может делать без запроса. Они не определяют, где вам, человеку, всё ещё нужно посмотреть, прежде чем действие будет выполнено. Это решение зависит от одного вопроса — того же, что отделяет безопасный режим от рискованного: каков худший исход, если это действие выполнится без проверки человеком? Чем ниже цена ошибки, тем больше можно пропускать без контроля. Чем выше цена и чем труднее отменить действие, тем больше шагу нужна точка контроля человеком перед выполнением.

Тот же вопрос о худшем сценарии определяет точку контроля независимо от того, пишет ли агент код или работает без присмотра в автоматизированном шаге, например в боте, который комментирует или блокирует pull request. Из этого следуют три варианта размещения:

  • Пропускайте низкорисковые, обратимые действия без точки контроля. Правка форматирования или изменение, ограниченное рабочим каталогом, несёт малую цену ошибки, поэтому требование одобрения человеком для каждого такого действия даёт избыточный контроль, который не нужен, и замедляет работу. Именно для этого случая создан режим acceptEdits .
  • Устанавливайте точку контроля для любого действия, которое трудно отменить или которое затрагивает чувствительный путь: запись вне рабочего каталога, деструктивная команда оболочки или правка файла, связанного с безопасностью или защищённого. Цена ошибки там высока, поэтому агент должен приостановиться и вынести действие на рассмотрение человеку, прежде чем оно выполнится. Правило deny обеспечивает это детерминированно, а режимы default или plan сохраняют запрос, пока вы принимаете решение.
  • Никогда не позволяйте агенту быть единственной точкой контроля для изменения кода, который ваша команда пометила как чувствительный. Здесь работа агента — это входные данные для решения человека, а не замена этому решению, поэтому человек должен просмотреть изменение перед слиянием, независимо от того, насколько уверенно звучит агент или его собственная проверка.

Размещение точки контроля и выбор режима разрешений — это одно и то же решение, рассматриваемое с двух сторон. Режим задаёт значение по умолчанию для всей сессии, а точка контроля — это место, где вы переопределяете это значение по умолчанию для того единственного действия, чья цена слишком высока, чтобы оставлять его на усмотрение умолчания; оба вытекают из вопроса о том, что сломается, если это выполнится без проверки.

Стоимость · Сложность · Риск

Стоимость: Работа в режиме default для доверенной работы добавляет задержку на подтверждение к каждому вызову инструмента, и это накапливается при длительном рефакторинге.

Сложность: Несколько уровней настроек и файлов с иерархией переопределений требуют постоянной внимательности. Правило deny на корпоративном уровне, противоречащее правилу allow на уровне проекта, должно быть понятно всем, кто поддерживает конфигурацию проекта.

Риск: Риск заключается в использовании неподходящего режима для контекста. Например, режим обхода, установленный из нетерпения на неизолированной машине, убирает все запросы безопасности между агентом и вашими рабочими файлами, а также, в отличие от других режимов, убирает защиту защищённых путей.

Устойчивый контекст проекта с помощью CLAUDE.md, файлов правил, хуков и субагентов

Ранее мы видели, как Claude Code контролирует действия через режимы разрешений и файлы настроек. Этот уровень конфигурации контролирует, что агенту разрешено делать.

Этот блок строится поверх него: теперь вы узнаете, как настроить то, что агент знает и как он себя ведёт, чтобы правила и контекст проекта, заданные вами в одной сессии, оставались в силе в начале следующей.

CLAUDE.md: файл проекта, загружаемый в каждую сессию

Каждый раз, когда Claude Code запускается в каталоге проекта, он ищет файл с именем CLAUDE.md в корне и читает его. Содержимое добавляется к вашему промпту до того, как придёт любое ваше сообщение. Это означает, что каждое соглашение, ограничение и команда, которые вы поместите в CLAUDE.md, присутствуют с первого промпта каждой сессии, без необходимости повторять их.

Команда /init сканирует вашу кодовую базу и генерирует стартовый CLAUDE.md. Сгенерированный файл — хороший базовый вариант, но его следует проверить перед использованием. Дорабатывайте его так, чтобы он содержал правила, влияющие на результат ваших промптов: команды тестирования, соглашения фреймворка, пути, которые агент не должен трогать, и стилистические решения, отличающиеся от значений по умолчанию.

Размер — основная причина сбоев. CLAUDE.md, который постоянно растёт с каждой новой инструкцией, может размывать самые важные правила. Больший файл занимает больше окна контекста, из-за чего любая отдельная инструкция составляет меньшую долю от загружаемого, а это снижает вероятность того, что агент последует именно тому правилу, которое предотвращает реальную ошибку. Держите в CLAUDE.md только ограничения, меняющие поведение, а всё остальное переносите в навыки (Skills), загружаемые по требованию.

Файлы правил: применение указаний только там, где они действуют

В предыдущем разделе мы установили, что CLAUDE.md загружается в каждую сессию и должен содержать инструкции, применимые ко всему проекту. Следующий вопрос — что делать с указаниями, актуальными только для одной части кодовой базы. Именно для этого нужны файлы правил: они позволяют применять инструкции только там, где они актуальны, вместо загрузки их в каждую сессию.

CLAUDE.md всегда активен, а файлы правил добавляют более узкий слой поверх этой базы. Они находятся в каталоге проекта .claude/rules/ и могут быть привязаны к конкретным путям с помощью glob-шаблона paths во frontmatter YAML. Правило, ограниченное таким образом, загружается в контекст только тогда, когда Claude Code работает с файлами, соответствующими шаблону, что позволяет применять правило к одной части кодовой базы, не загромождая остальной контекст.

Обратите внимание, что область действия определяется frontmatter, а не расположением файла. Файлы правил можно организовать в подкаталоги .claude/rules/ (например, .claude/rules/database/), но эта структура носит только организационный характер; файл правил без поля paths загружается безусловно при запуске, с тем же приоритетом, что и CLAUDE.md, независимо от того, где он находится внутри .claude/rules/.

На практике широкую память проекта и универсальные ограничения помещайте в CLAUDE.md, а узкие, специфичные для пути указания — в файлы правил с областью действия paths. Ограничение вроде «никогда не изменять схему базы данных» находится в CLAUDE.md, потому что применяется везде. Ограничение вроде «весь SQL в модуле базы данных должен включать явную границу транзакции» находится в .claude/rules/database.md с таким frontmatter:

--- paths: - "src/db/**/*.sql" ---

так что оно попадает в контекст только тогда, когда Claude работает с этими файлами.

Хуки: запуск собственных скриптов в фиксированных точках жизненного цикла

Хук позволяет перехватывать и контролировать вызовы инструментов до или после их выполнения. Когда вы пишете конкретное правило в CLAUDE.md, говорящее агенту запускать Prettier после каждой правки файла, агент будет следовать ему большую часть времени. В противном случае хук делает это происходящим абсолютно каждый раз без исключений, потому что хук срабатывает независимо от того, что решает модель.

Хуки определяются в файлах настроек и настраиваются с помощью команды /hooks. Каждый хук привязан к событию жизненного цикла, необязательному сопоставителю (matcher), ограничивающему его определёнными типами инструментов, и команде, которая выполняется при срабатывании события. Основные события для большинства случаев использования — контроль и автоматизация:

  • PreToolUse: Выполняется перед вызовом инструмента. Поскольку он запускается первым, хук PreToolUse может изучить вызов инструмента и завершиться с кодом 2, чтобы заблокировать его, записав причину в stderr в качестве обратной связи, которую видит агент. Так вы обеспечиваете контроль доступа на уровне конфигурации, а не надеетесь, что агент соблюдает инструкцию CLAUDE.md.
  • PostToolUse: Выполняется после завершения вызова инструмента. Поскольку вызов уже произошёл, это событие не может его заблокировать, что делает его подходящим местом для автоматизированных побочных эффектов: запуска форматтера кода после правки, запуска тестов после изменения файла или логирования операции для аудита.
  • UserPromptSubmit: Выполняется, когда вы отправляете промпт, до того как модель его обработает. Используйте, когда нужно внедрить контекст или проверить запрос до начала работы.
  • Stop: Выполняется, когда модель завершает ответ. Используйте для последующих действий, относящихся к концу хода: уведомлений, задач очистки или фиксации журнала аудита.
  • Notification: Выполняется, когда Claude Code отправляет уведомление, что происходит, когда Claude нужно разрешение на использование инструмента или после 60 секунд бездействия Claude Code. Используйте для маршрутизации этих сигналов во внешний канал или систему логирования.
  • SessionStart: Выполняется при старте или возобновлении сессии. Используйте для инициализации состояния, проверки переменных окружения или подтверждения доступности необходимых сервисов перед началом работы агента.
  • SessionEnd: Выполняется при завершении сессии. Используйте для задач завершения, финальных записей аудита или уведомлений о закрытии сессии.

Хук, блокирующий правки продакшен-конфигурации с помощью события PreToolUse, обеспечивает соблюдение этого ограничения при каждом вызове инструмента в каждой сессии, независимо от режима разрешений. В этом разница между гарантией (guardrail) и соглашением.

Субагенты: делегирование работы в изолированный контекст

субагент — это специализированный ассистент, которому Claude Code может делегировать задачи, и каждый такой ассистент выполняет задачу в своём собственном отдельном контексте и возвращает только свой результат. Он не наследует историю вашей основной беседы, файлы, накопленные в контексте, или текущее состояние сессии. Когда вы отправляете задачу субагенту, он начинает с чистого листа, выполняет работу и возвращает результат.

Встроенные субагенты различаются тем, что они загружают при старте; это различие определяет, как применяются правила вашего проекта. Всегда сверяйтесь с актуальным списком в документации Claude Code, поскольку набор со временем расширялся, но знайте, что конкретное разделение, влияющее на правила вашего проекта, сохраняется в разных версиях. Встроенные субагенты Explore и Plan пропускают CLAUDE.md и git status, чтобы исследование было быстрым и дешёвым. Они оптимизированы под скорость, поэтому правила уровня проекта и состояние репозитория, заданные в CLAUDE.md, отсутствуют в их контексте при работе. Универсальный (general-purpose) субагент загружает оба. Если вы делегируете задачу Explore или Plan, а правило из вашего CLAUDE.md применимо, значит, этот контекст не был загружен. Для задач, где ограничения проекта должны соблюдаться, используйте универсальный субагент или пользовательский субагент, явно загружающий нужные правила.

Пользовательские субагенты также не видят ваши навыки автоматически. Если вы определяете пользовательский субагент в .claude/agents и ему нужен конкретный навык, вы должны явно указать этот навык во frontmatter агента. У встроенных агентов нет предзагруженных навыков. Если встроенному агенту нужно поведение на основе навыка, правильный путь — создать пользовательский субагент с этими навыками, перечисленными в его конфигурации.

Упаковка рабочего процесса в плагин: навыки, пользовательские команды и установка из маркетплейса

Ранее мы рассмотрели механизмы, которые дают Claude Code устойчивый контекст и обеспечивают соблюдение поведения: CLAUDE.md для постоянно активной памяти проекта, файлы правил для ограниченных указаний, хуки для детерминированных гарантий и субагенты для изолированного делегирования задач.

Эти механизмы находятся в вашем каталоге .claude и версионируются вместе с проектом. Теперь перейдём к следующему вопросу: как упаковать эту настройку так, чтобы коллега мог установить её одним простым шагом, вместо того чтобы вручную повторять вашу конфигурацию?

Навыки — это переиспользуемые рабочие процессы, которые агент загружает по требованию

навык — это переносимый Markdown-файл (файл SKILL.md), размещённый в .claude/skills. Frontmatter определяет навык и описывает, когда он применяется, а тело содержит шаги. Один и тот же навык может работать в Claude Code, вызываться через Messages API или загружаться Agent SDK. Между этими тремя вариантами меняется не сам файл, а то, где навык выполняется, как он загружается и к чему ему разрешено прикасаться. Разработчик, видевший навыки только в Claude Code, может делать допущения, не верные для API, поэтому этот раздел описывает различия.

Как навык загружается и выполняется в каждом из вариантов

Выберите каждую вкладку, чтобы узнать, как загружается навык, где выполняются шаги и что нужно знать.

Как загружается навык: Обнаруживается из .claude/skills в файловой системе. Загружается при совпадении описания или при явном вызове по имени.

Где выполняются шаги: В вашей терминальной сессии, на ваших локальных файлах, в рамках активного режима разрешений и правил deny.

Что нужно знать: Он основан на файловой системе и управляется уровнем настроек.

Как загружается навык: Отправляется вместе с запросом и выполняется внутри контейнера выполнения кода, а не в среде вашего приложения. Требует бета-заголовков code-execution и skills.

Где выполняются шаги: Внутри контейнера выполнения кода Anthropic, а не на вашей машине. Файловая система навыка и доступ к инструментам — это то, что предоставляет этот контейнер.

Что нужно знать: Навык, который предполагает наличие локальных файлов или локальных инструментов, здесь будет вести себя иначе, потому что выполняется не там, где находятся эти файлы.

Как загружается навык: Загружается агентом, которым управляет SDK, но то, загружаются ли настройки файловой системы (CLAUDE.md, навыки), контролируется конфигурацией settingSources. Не полагайтесь на значение по умолчанию: всегда задавайте его явно нужными источниками и сверяйте текущее поведение по умолчанию со справочником Agent SDK на момент сборки. Задаётся через «settingSources» (TypeScript) / «setting_sources» (Python).

Где выполняются шаги: В процессе, которым управляет SDK, то есть в вашей среде, как только вы указали ему загружать источники файловой системы.

Что нужно знать: Типичный сюрприз: навык, работавший в Claude Code, ничего не делает под SDK, потому что settingSources никогда не был задан, и навык так и не загрузился.

Как загружается навык: Определяется один раз как ресурс API, называющий модель, системный промпт, инструменты, MCP-серверы и навыки. Anthropic загружает навык на стороне сервера при запуске агента, поэтому на вашей стороне нет шага обнаружения через файловую систему.

Где выполняются шаги: Внутри песочницы, которую предоставляет и запускает Anthropic, а не в вашей среде. Ваше приложение отправляет пользовательские события и считывает потоковые результаты обратно. Навык имеет доступ к тому, что предоставляет эта управляемая песочница, а не к вашим локальным файлам.

Что нужно знать: В настоящее время это публичная бета-версия, требующая бета-заголовка managed-agents-2026-04-01, и сессии хранятся на стороне сервера, что означает, что Managed Agents в настоящее время не подходят под Zero Data Retention или покрытие HIPAA BAA. Навыки прикрепляются при определении ресурса агента, а не во время сессии. Обновите определение агента, чтобы изменить доступные навыки.

Три правила переносимости

  • Пишите описание как критерий сопоставления. Модель загружает навык, сравнивая ваш запрос с его описанием, поэтому описание, чётко определяющее, когда навык применим, работает в любой среде выполнения, а расплывчатое не загрузится ни в одной из них.
  • Не предполагайте, что внутри тела навыка существует локальная файловая система или локальные инструменты. Навык, вызывающий локальную команду через shell, работает в Claude Code, но ломается в Messages API, где он выполняется в контейнере без команды. Ограничивайте шаги навыка тем, что гарантированно предоставляет среда выполнения, либо документируйте зависимость.
  • Помните, что субагенты не наследуют навыки. Это было верно в Модуле 2 и остаётся верным здесь: субагент стартует с чистого листа, поэтому навык, на который полагался родитель, должен быть явно перечислен для субагента в каждой среде выполнения, поддерживающей субагенты.

Практический вывод в том, что вы можете написать навык один раз и переиспользовать его, но нужно специально проектировать его с расчётом на использование в разных терминалах. Навык, ограниченный чётким описанием и свободный от допущений о локальной среде, переносится между средами выполнения без проблем, а тот, что предполагает конкретную локальную среду, — нет.

Явная точка входа для рабочего процесса

Пользовательская команда — это ярлык для определённой процедуры. В текущей версии Claude Code навыки — рекомендуемый формат как для явного, так и для автоматического вызова: вы вызываете навык напрямую с помощью /skill-name, либо Claude загружает его автоматически, когда это уместно. Старый формат каталога .claude/commands/ всё ещё работает, но считается устаревшим процессом. Используйте навыки с disable-model-invocation: true во frontmatter, когда нужен рабочий процесс, который запускается только при явном вызове.

Команды плагинов автоматически получают пространство имён: имя плагина становится префиксом, поэтому команда run-tests в плагине с именем payments вызывается как /payments:run-tests. Именно поэтому два плагина могут одновременно поставлять команду run-tests без конфликтов. Авторам следует относиться к имени плагина как к части интерфейса, поскольку оно становится префиксом каждой поставляемой команды, и учитывать, что переименование плагина переименовывает их все.

Уровень упаковки, делающий настройку устанавливаемой

плагин объединяет навыки, хуки, субагенты и MCP-серверы в единый устанавливаемый пакет. Плагины можно упаковывать и распространять через маркетплейс — каталог плагинов, созданных и опубликованных кем-то другим. Официальный маркетплейс Anthropic доступен автоматически при запуске Claude Code, а сторонние маркетплейсы, размещённые в репозитории GitHub, можно добавить с помощью команды вроде /plugin marketplace add <owner/repo>. После этого коллеги могут выполнить одну простую команду установки, чтобы получить ту же настройку. Плагин заменяет страницу ручных шагов настройки версионированной, проверяемой установкой. Плагин размещает компоненты следующим образом:

  • Навыки размещаются в каталоге навыков.
  • Хуки, субагенты и настройки размещаются в соответствующих местах.

Манифест плагина описывает пакет, а команда установки подключает его к целевой установке. Плагины могут скачиваться отдельными людьми или на уровне всей организации.

Администраторы предприятия могут развёртывать плагины в масштабах всей организации через управляемые настройки. Список разрешённых маркетплейсов (managed marketplace allowlist) определяет, какие источники маркетплейсов пользователи могут добавлять, так что организация контролирует, откуда могут поступать плагины. Этот список ограничивает то, что пользователи могут добавить, но не регистрирует маркетплейсы автоматически. Если вы хотите распространить маркетплейс на всех пользователей, не требуя от них самостоятельно выполнять команду добавления, сочетайте настройку allowlist с extraKnownMarketplaces в управляемых настройках. Приоритет определяется областью развёртывания: поскольку управляемые настройки находятся выше пользовательских и проектных настроек в иерархии конфигурации, плагин, развёрнутый на управляемом уровне, имеет приоритет и не может быть переопределён пользователями или файлами проекта. Сверьтесь со справочным слоем для точных названий настроек.

Плагин, который установился у вас на машине и не сработал у всех остальных

Настройка

Чистая установка плагина говорит о том, что пакет был собран правильно; однако это не означает, что плагин будет эффективно работать, потому что установка и выполнение — разные вещи. Установка копирует файлы на место. Выполнение разрешает пути и переменные, на которые указывают эти файлы, применительно к машине, на которой они выполняются. Когда автор плагина закладывает структуру своей собственной машины в навык, установка по-прежнему проходит успешно везде, но выполнение проваливается везде, кроме собственной настройки автора. Этот разрыв возникает потому, что автор не может это увидеть.

Что произошло

Разработчик создал навык рабочего процесса развёртывания, упаковал его в плагин и протестировал локально. Локальное тестирование прошло успешно, плагин был опубликован для команды через внутренний маркетплейс, установка прошла успешно у каждого коллеги, но в момент, когда любой коллега запускал навык, происходил сбой.

Первопричина находилась в SKILL.md навыка, в команде, указывавшей на /Users/alexmorgan/projects/deploy-utils/validate.sh.

. Этот каталог существовал только на машине автора и больше нигде. Навык содержал абсолютный путь к домашнему каталогу автора, поэтому при каждом запуске у коллеги искался файл, который был только в системе автора.

Второй навык в том же плагине опирался на переменную окружения DEPLOY_TOKEN, которую автор задал в своём собственном профиле оболочки, а README плагина её никогда не упоминал. Три коллеги потратили два часа на отладку, прежде чем проследили вторую ошибку до отсутствующей переменной.

Плагин ошибочно рассматривал машину автора как машину команды, что и вызвало сбой. Оба сбоя в примере выше имеют одну и ту же первопричину и один и тот же абсолютный путь. Он находится в SKILL.md в виде обычного текста, и рецензент, читающий файл, может это заметить. Именно поэтому исправление может стоить трём людям двух часов.

На что обратить внимание

Любая ссылка на путь в навыке, команде хука или компоненте плагина должна быть относительной к корню проекта или использовать переменную окружения для базового пути. Используйте $CLAUDE_PROJECT_DIR для ссылки на скрипты, хранящиеся в проекте, и ${CLAUDE_PLUGIN_ROOT} для скриптов, встроенных внутрь самого плагина, чтобы путь разрешался корректно независимо от того, чья это машина или в каком каталоге началась сессия. Убедитесь, что любые скрипты, конфигурационные файлы или другие ресурсы, от которых зависит плагин, либо встроены внутрь плагина, либо находятся в общем расположении проекта, чтобы каждый коллега мог получить доступ к тем же файлам после установки. Документируйте каждую переменную окружения, которую требует плагин, и проверяйте её при установке, чтобы отсутствующая переменная проявилась сразу, а не в середине выполнения. Затем протестируйте установку на чистой машине перед распространением; это поможет выявить проблемы, которые может скрывать машина сборки.

ТеорияMCP-серверы·21 мин

Создание и настройка MCP-сервера: транспорт, область действия и сервер GitHub

Предыдущие разделы представили плагины как уровень упаковки, объединяющий навыки, хуки, субагенты и MCP-серверы в единый устанавливаемый пакет.

Этот раздел подробнее объясняет, что такое пакеты MCP-серверов и как их создавать. MCP-сервер — это уровень, который предоставляет Claude инструменты извне вашей кодовой базы. При создании MCP-сервера одно из первых решений — определить подходящий механизм транспорта и задать область действия сервера.

Что такое MCP-сервер и чем он отличается от прямого подключения инструмента?

При прямом подключении инструмента в приложение вы отвечаете за определение схемы инструмента и его функциональности. Оба находятся в коде этого приложения. Если трём разным приложениям нужен доступ к одному и тому же внешнему сервису, каждое из них поддерживает собственную интеграцию.Model Context Protocol, или MCP, отделяет определения инструментов от отдельных приложений и превращает их в процесс, называемый сервером.

MCP-сервер — это процесс, предоставляющий инструменты, ресурсы и промпты, которые могут использовать MCP-клиенты. У Claude Code есть встроенный MCP-клиент. Когда вы подключаетесь к MCP-серверу, Claude Code обнаруживает предоставляемые им инструменты и может вызывать их во время сессии. С MCP-сервером вы создаёте функциональность один раз, и каждый MCP-клиент, подключающийся к нему, получает доступ без повторной реализации интеграции.

MCP-серверы также предоставляют ресурсы и промпты

MCP-сервер предоставляет инструменты, ресурсы и промпты. Об инструментах мы уже узнали: это действия, которые модель может вызывать. Два других понятия покрывают случаи, когда вызов инструмента не даёт того, что нужно.

ресурс — это данные только для чтения, которые сервер предоставляет клиенту для получения и помещения прямо в контекст, вместо того чтобы модель вызывала инструмент для их получения. Клиент запрашивает ресурс по его адресу, а сервер возвращает данные. Ресурсы бывают двух видов: прямой ресурс имеет фиксированный адрес для данных, не принимающих параметров, например список доступных документов, а шаблонный ресурс включает параметр в адрес, например адрес документа, принимающий идентификатор документа. Обращайтесь к ресурсу, когда хотите, чтобы известные данные были в контексте с самого начала хода. Это нужно, когда прямое получение ресурса дешевле и предсказуемее, чем вызов инструмента для его получения. Поддержка ресурсов различается между MCP-клиентами; убедитесь, что у вашего клиента есть механизм внедрения ресурсов в контекст, прежде чем полагаться на этот паттерн.

промпт — это заранее написанный шаблон инструкции, который сервер предоставляет, чтобы клиент мог вызвать проверенный промпт по имени, вместо того чтобы просить каждого пользователя писать свой собственный. Пользователь уже может попросить модель выполнить большинство задач своими словами, поэтому промпт полезен, когда нужна конкретная формулировка: задача, где тщательно составленная инструкция даёт заметно лучшие результаты, чем то, что напечатал бы пользователь, и где вы хотите, чтобы каждый клиент получал одинаковое качество. Упаковка инструкции на сервере означает, что промпт поддерживается в одном месте и переиспользуется везде, где подключён сервер.

Транспорт: как Claude Code общается с сервером

Транспорт — это канал связи между MCP-клиентом и MCP-сервером. Правильный транспорт зависит от того, где выполняется сервер. Выберите каждую вкладку, чтобы узнать, что это такое и когда это использовать.

stdio запускает сервер как локальный процесс на той же машине, что и клиент. Клиент запускает сервер как подпроцесс и общается через стандартный ввод и вывод. Это правильный выбор для локального инструмента, личного скрипта или сервера разработки, который вы запускаете на своей машине. Это не работает для сервера, который вы хотите распространить на всю команду или разместить удалённо.

HTTP — рекомендуемая форма транспорта для любого сервера, который не работает локально. Он подключается через стандартное HTTP-соединение и поддерживает серверы, размещённые на другой машине. При регистрации HTTP-сервера вы указываете URL, и клиент подключается по сети. Общие командные серверы и размещённые интеграции используют HTTP.

SSE (Server-Sent Events) — это более старое средство транспорта, предшествующее текущему HTTP-транспорту. Оно было вытеснено HTTP-транспортом и больше не рекомендуется для новых серверов. Если вы встретите SSE в существующей конфигурации или документации, относитесь к нему как к устаревшему варианту, а не как к актуальной рекомендации.

Стоимость по контексту

Каждый подключённый MCP-сервер добавляет определения инструментов, которые заняли бы окно контекста, если бы загружались заранее. По умолчанию Claude Code откладывает эти определения, вместо того чтобы загружать их заранее, и использует шаг поиска, чтобы обнаружить и загрузить нужные инструменты только тогда, когда этого требует задача. В контекст попадают только вызванные инструменты.

Опциональный режим загружает определения инструментов заранее, когда они укладываются примерно в 10 процентов окна контекста, откладывая загрузку только при превышении этого предела. В любом случае подключение только нужных серверов делает каждый запрос компактнее, поскольку каждый подключённый сервер добавляется в пул определений, которые должна учитывать модель.

Кэширование промптов: платить один раз за переиспользуемые запросы

Проблема стоимости контекста, которую вы только что видели на примере MCP-серверов, имеет измерение и стоимости, и окна. Каждый запрос заново обрабатывает свои входные данные с нуля, включая те части, которые были идентичны в прошлом запросе, а значит, вы платите за повторную обработку каждый раз. Кэширование промптов может избавить вас от повторной оплаты одного и того же стабильного содержимого.

Кэширование сохраняет работу по обработке, проделанную над стабильным префиксом вашего запроса, чтобы последующий запрос мог переиспользовать её вместо повторной обработки тех же токенов. Первый запрос записывает префикс в кэш, а последующие запросы отправляют идентичное содержимое до той же точки кэша за малую долю стоимости. Содержимое должно совпадать точно: один изменённый символ до точки кэширования делает этот кэш недействительным и вынуждает выполнить новую запись. Именно поэтому наиболее подходящие кандидаты для кэша — это части запроса, которые редко меняются, такие как длинный системный промпт, большой набор определений инструментов или справочный документ, по которому вы задаёте несколько вопросов.

Вы включаете кэширование, отмечая точку разрыва кэша (cache breakpoint); глобальной настройки, включающей кэширование, не существует. В Messages API вы добавляете поле cache_control типа ephemeral к последнему блоку, который хотите закэшировать; это кэширует всё вплоть до этого блока включительно. Можно разместить до четырёх точек разрыва. Запрос обрабатывается в фиксированном порядке: инструменты, системный промпт и сообщения, поэтому точка разрыва после инструментов кэширует определения инструментов, оставляя сообщения динамическими.

У кэша есть ограничение по времени. Время жизни кэша по умолчанию — пять минут с момента последнего чтения. Дополнительно доступно время жизни в один час, если задать ttl равным 1h в точке разрыва. Значение по умолчанию в пять минут подходит для модели диалога «вопрос-ответ», где запросы поступают каждые несколько минут, поскольку каждое чтение сбрасывает таймер. Часовой вариант подходит для нагрузки с более длинными паузами между запросами, например для агента, делающего паузы между шагами, где пятиминутное окно истекло бы до следующего запроса. Если окно истекает до следующего запроса, вы снова платите за запись, не получая выгоды от чтения. Обратите внимание, что кэширование применяется только выше минимального порога токенов (1024 токена для большинства современных моделей), поэтому короткие промпты не будут кэшироваться, даже если задана точка разрыва.

Генерация с расширенным поиском: как Claude подключает только те знания, которые нужны запросу

Проблема стоимости контекста, которую вы только что видели на примере MCP-серверов, — та же самая, которую создаёт большой объём справочного материала. Модель читает всё в своём окне контекста для каждого запроса, поэтому чем больше документов вы загружаете заранее, тем больше контекста используется и тем меньше места остаётся для работы. Генерация с расширенным поиском, обычно сокращаемая до RAG, — это паттерн, решающий эту проблему. Вместо загрузки каждого документа в контекст система хранит материал вне окна контекста, находит части, наиболее релевантные текущему запросу, и предоставляет модели только эти части в момент запроса. Затем модель генерирует ответ на основе этого извлечённого фрагмента, а не всей библиотеки.

RAG существует в двух формах:

Классический RAG выполняет всю сложную работу заранее. Прежде чем кто-либо задаст вопрос, исходный материал разбивается на фрагменты, и каждый фрагмент преобразуется в набор чисел (называемый эмбеддингом), математически отражающий его смысл. Эти числа хранятся в базе данных. Когда пользователь задаёт вопрос, система преобразует вопрос в такой же тип чисел, а затем находит фрагменты с наиболее похожими числами. Представьте это как библиотекаря, который ещё до открытия библиотеки прочитал каждую книгу и написал точную карточку-резюме для каждой главы, поэтому, когда вы приходите с вопросом, он может мгновенно достать нужные карточки.

Агентный поиск полностью пропускает предварительную индексацию. Заранее созданной базы данных нет. Вместо этого модель определяет, что ей нужно, в момент вашего запроса, а затем идёт и получает это: ищет в живых источниках, читает документы по требованию, подтягивает результаты по мере развития задачи. Представьте это как исследователя, который, когда вы задаёте вопрос, сам идёт и находит ответ, а не сверяется с заранее подготовленными карточками.

Возможно, вы уже сталкивались с агентным поиском, не зная его названия. В Claude Code, когда вы подключены ко многим внешним инструментам (MCP-серверам), Claude не загружает все определения инструментов заранее — это было бы слишком много, чтобы держать одновременно. Вместо этого он обнаруживает и загружает только те инструменты, которые нужны для текущей задачи. Claude.ai Projects работает так же с загруженными документами: когда база знаний проекта становится больше, чем может поместиться в активном окне, он показывает только те разделы документов, которые наиболее релевантны каждому вопросу, вместо загрузки всего.

Оба подхода делают одно и то же по сути: оба находят релевантный фрагмент материала и генерируют ответ на его основе. Разница — во времени: классический RAG находит фрагмент, сопоставляя его с заранее построенным индексом; агентный поиск находит его, выполняя поиск в момент необходимости.

Прежде чем обращаться к поиску, стоит понимать два его свойства:

  • Он масштабируется. По мере роста исходного материала стоимость каждого запроса остаётся неизменной, потому что модель всегда получает только фрагмент, релевантный этому вопросу, а не всю библиотеку. База знаний может вырасти до тысяч документов, и один вопрос всё равно вернёт примерно тот же объём текста. Именно это позволяет поиску работать в масштабе: источник может продолжать расти без роста самого запроса.
  • Он хорош настолько, насколько хорошо то, что он находит. Модель рассуждает над полученным фрагментом. Если шаг извлечения пропускает нужный документ, модель никогда его не увидит. Это означает, что то, как вы организуете свой материал, важно: файлы с расплывчатыми именами («notes_final_v3.pdf») труднее найти, чем файлы с описательными именами («Политика возврата за Q3, обновлено в августе 2024»). Группировка связанных файлов тоже помогает. Хороший поиск начинается с хорошо организованного источника.

Область конфигурации: кто загружает сервер

Область действия определяет, какие пользователи и проекты загружают сервер. Каждая область соответствует своему расположению конфигурации.

  • Локальная область хранит конфигурацию сервера в ~/.claude.json в привязке к пути текущего проекта. Она применяется только к проекту, над которым вы сейчас работаете, и не передаётся коллегам. Это правильная область для сервера, привязанного к контексту конкретного проекта, который вы ещё не готовы закоммитить в репозиторий, или для инструментов, имеющих смысл только в одном проекте.
  • Пользовательская область хранит конфигурацию сервера в ваших личных настройках Claude и делает его доступным во всех ваших проектах. Она по-прежнему персональна: коллеги её не видят, и она не записывается в репозиторий. Это правильная область для личной утилиты, которую вы используете в каждом проекте, например локального инструмента для работы с базой данных или скрипта, на который вы полагаетесь независимо от того, с какой кодовой базой работаете.
  • Область проекта записывает конфигурацию сервера в файл .mcp.json в корне репозитория. Когда этот файл закоммичен в систему контроля версий, каждый, кто клонирует репозиторий, автоматически получает тот же сервер. Это правильная область для сервера, к которому должна иметь доступ вся команда, поскольку конфигурация перемещается вместе с кодом. Одна вещь, которую стоит учитывать: сервер с областью проекта запускается с машины каждого коллеги. Для stdio-сервера закоммиченная конфигурация хранит команду запуска, и каждый клон порождает собственный локальный подпроцесс, поэтому каждому коллеге нужна установленная локально среда выполнения (например, Node для сервера, запускаемого через npx).
  • Корпоративная область развёртывается через централизованно управляемую конфигурацию, контролируемую администратором. Администраторы могут распространять серверы на всех пользователей организации без индивидуальных шагов настройки. Это правильная область для общих внутренних сервисов, инструментов безопасности или любого сервера, который должен присутствовать во всей организации и не может быть оставлен на усмотрение отдельных разработчиков.

Правила разрешений, нацеленные на отдельный инструмент MCP, а не на весь сервер

Подключение сервера открывает доступ ко всему списку его инструментов, но редко нужно, чтобы агент обращался к каждому из этих инструментов без проверки. Уровень разрешений из раздела о режимах разрешений распространяется и на инструменты MCP, и правила могут называть отдельный инструмент, а не весь сервер.

Инструмент MCP идентифицируется в правиле разрешений по имени сервера и инструмента: mcp__server__tool. Правило allow для mcp__github__create_issue позволяет этому единственному инструменту работать без запроса, в то время как каждый другой инструмент на сервере GitHub по-прежнему запрашивает подтверждение. Правило deny для инструмента, способного к записи, блокирует его, в то время как инструменты только для чтения на том же сервере остаются доступными. Так вы подключаете широкий сервер, но удерживаете агента в узких рамках того, что ему разрешено делать. Deny для одного инструмента переопределяет allow для сервера.

Коннектор MCP в API — ещё один полезный элемент управления. Если вы обращаетесь к серверу через коннектор MCP в API, объект mcp_toolset позволяет задать флаг enabled для каждого инструмента. Этот флаг позволяет зарегистрировать сервер, но показать модели только конкретные нужные инструменты. Правило разрешений решает, может ли выставленный инструмент выполняться; флаг enabled решает, видит ли модель этот инструмент вообще. Первое — это элемент управления, второе — элемент контроля стоимости контекста и области видимости. Эти элементы управления часто используются вместе. Всегда сверяйте точный синтаксис правил и бета-заголовок коннектора с документацией перед публикацией.

MCP-сервер GitHub: транспорт, область действия и аутентификация на конкретном примере

MCP-сервер GitHub — это удалённый сервер, поддерживаемый GitHub, предоставляющий инструменты для управления репозиторием, включая просмотр pull request'ов, открытие issue, поиск по коду и многое другое. Пройдя через процесс подключения, вы увидите, как транспорт, область действия и аутентификация работают вместе на сервере, поддерживаемом кем-то другим.

Сервер GitHub использует HTTP-транспорт, потому что размещён удалённо на стороне GitHub. Вы регистрируете его, указывая URL сервера, и клиент подключается по сети. Для области действия выбирайте область проекта, когда доступ к тем же инструментам репозитория нужен всей команде, и локальную область, когда доступ к серверу нужен только вам.

Аутентификация для MCP-сервера GitHub использует персональный токен доступа (Personal Access Token). Вы создаёте токен в GitHub, затем передаёте его как Bearer-токен в заголовке запроса конфигурации MCP. Токен должен передаваться через переменную окружения и упоминаться в конфигурационном файле. Он не должен быть закоммичен напрямую в .mcp.json, потому что токен, записанный прямо в закоммиченный файл, попадает в историю репозитория и не может быть удалён путём перезаписи файла в более позднем коммите.

OAuth — это другой механизм аутентификации, используемый серверами, где сервис аутентифицирует отдельных пользователей через процесс входа в браузере. Linear — пример сервера, использующего этот паттерн. При первом подключении к MCP-серверу Linear клиент перенаправляет на страницу входа Linear. После того как вы одобрите доступ, выдаётся токен, который сохраняется автоматически. Никто не копирует учётные данные вручную. OAuth — правильный паттерн для любой интеграции, где модель авторизации сервиса привязана к личности пользователя.

MCP GitHub использует служебные учётные данные, которые вы создаёте и храните; MCP Linear запускает процесс входа, который сам обрабатывает учётные данные за вас. Оба являются удалёнными HTTP-серверами и следуют одной и той же логике транспорта и области действия. Различается именно шаг аутентификации.

За командами, не управляющими секретами окружения тщательно, стоит внимательно следить. Добавление MCP-серверов увеличивает число мест, где секрет может быть неправильно обработан. Риск концентрируется в файле .mcp.json, который коммитится в репозиторий.

Сервер работал, команде была нужна общая настройка, и очистка метода аутентификации казалась делом, которое можно сделать после передачи проекта. Этот шорткат превратил временный жёстко прописанный API-ключ в общедоступную утечку учётных данных в момент, когда конфигурационный файл был закоммичен.

Что произошло

Разработчик подключился к MCP-серверу хранилища данных, используя ключ API сервисного аккаунта. Чтобы быстро запустить сервер во время настройки, ключ был помещён прямо в конфигурационный файл .mcp.json . План состоял в том, чтобы перенести его в переменную окружения перед распространением настройки на команду.

Разработчик закоммитил .mcp.json в репозиторий проекта, чтобы коллеги могли подключаться к тому же серверу, клонируя репозиторий, и ключ был закоммичен вместе с ним. В течение 48 часов три коллеги склонировали репозиторий, а CI-пайплайн запустил свежий клон. Ключ теперь находился в четырёх местах: на локальной машине, в истории репозитория, на трёх машинах коллег и в файловой системе CI-раннера.

Осознав это, разработчик перенёс ключ в переменную окружения, обновил .mcp.json и закоммитил исправленный файл. Но ключ всё ещё оставался в истории коммитов, и учётную запись сервиса пришлось ротировать. Ротация сломала два внешних сервиса, настроенных с тем же ключом, и это заняло три часа работы на исправление.

Исправленный .mcp.json использует ссылку на переменную окружения вместо встроенного значения:

До (не используйте)

{ "type": "http", "url": "https://warehouse.internal/mcp", "headers": { "Authorization": "Bearer sk-abc123..." .............встроенные учётные данные } }

После (правильно)

{ "type": "http", "url": "https://warehouse.internal/mcp", "headers": { "Authorization": "Bearer ${WAREHOUSE_MCP_TOKEN}" ............ссылка на переменную окружения } }
На что обратить внимание

API-ключи, закоммиченные в конфигурационный файл, попадают в историю репозитория. Перезапись файла в более позднем коммите не удаляет ключ из истории; она удаляет его только из текущей версии. Любые учётные данные, записанные напрямую в закоммиченном файле, следует считать скомпрометированными и ротировать. Правильный паттерн — поместить значение в переменную окружения и ссылаться на переменную в конфигурационном файле.

Чтобы не допустить записи агентом значений учётных данных напрямую в закоммиченные файлы, используйте два уровня. Во-первых, добавьте в CLAUDE.md инструкцию-соглашение о том, что значения учётных данных никогда не должны записываться напрямую в .mcp.json. Это сигнализирует правило модели в каждой сессии. Во-вторых, подкрепите эту инструкцию хуком PreToolUse, который проверяет операции записи и правки для .mcp.json на наличие паттернов, похожих на встроенные значения учётных данных, и завершается с кодом, блокирующим операцию при обнаружении такого паттерна. Инструкция в CLAUDE.md сообщает намерение; хук обеспечивает его детерминированно независимо от того, что решает модель. Это то же различие между хуком и инструкцией, что было рассмотрено в разделе об устойчивом контексте проекта: инструкция в CLAUDE.md может соблюдаться непоследовательно, когда файл растёт или контекст смещается, а хук срабатывает при каждом релевантном вызове инструмента без исключений.

Почему корпоративная интеграция отличается от рабочего прототипа

Прототип, подключающий Claude к внутреннему сервису, отвечает на один вопрос: работает ли подключение? Продакшен-интеграция уровня предприятия должна ответить на несколько дополнительных вопросов: от чьего имени действует модель и можно ли аудировать эту идентичность? К каким данным у неё есть доступ и куда эти данные уходят за пределы организации? Может ли администратор заблокировать конфигурацию так, чтобы ни один отдельный разработчик не мог изменить настройку аутентификации? Можно ли логировать доступ так, чтобы это удовлетворяло аудиту на соответствие требованиям?

Эти вопросы не новы для корпоративного ПО; они предполагают те же требования к идентичности, доступу и соответствию нормам, что применяются к любой внешней системе, затрагивающей регулируемые данные. Рассмотрение их как части дизайна интеграции — вот что отличает демо от готового к развёртыванию решения.

Паттерны аутентификации по типу сервиса

Правильный механизм аутентификации зависит от того, где выполняется сервис и какую модель идентичности он поддерживает. Выберите каждую вкладку, чтобы узнать паттерн и когда его использовать.

Используйте OAuth. MCP-сервер возвращает 401 Unauthorized, сигнализируя о необходимости аутентификации. Клиент инициирует процесс входа через браузер. После того как пользователь одобряет доступ, выдаётся токен и сохраняется. Никто не копирует секрет вручную; поток OAuth — ожидаемый паттерн для облачных сервисов, SaaS-инструментов и любой интеграции, где идентичность пользователя является частью модели авторизации. MCP-сервер Linear, рассмотренный ранее в этом модуле, использует этот паттерн; сервер GitHub, напротив, аутентифицируется с помощью персонального токена доступа, передаваемого как заголовок.

Используйте API-ключ, передаваемый через переменную окружения. Ключ идентифицирует сервисный аккаунт. Ключ никогда не должен коммититься в конфигурационный файл; он находится в окружении в момент выполнения. Для CI-пайплайна, использующего Agent SDK, ключ внедряется как секрет раннером пайплайна, а не встраивается в код.

stdio-транспорт без сетевой аутентификации. Граница безопасности — это модель разрешений файловой системы. Правило deny в файлах настроек — это уровень управления.

Управление самим секретом — вторая половина безопасной аутентификации. Учётные данные никогда не должны перемещаться вместе с конфигурацией, которая на них ссылается: конфигурационный файл содержит только ссылку на переменную, а значение находится в переменной окружения или в управляемом хранилище секретов, внедряемом в момент выполнения. Храните ключи сервисных аккаунтов в менеджере секретов, а не в файлах, и ротируйте их по расписанию и немедленно после любой предполагаемой утечки. Если ключ утёк, его нужно ротировать, но помните: значение, встроенное в закоммиченный код, ротировать нельзя. Ограничивайте каждые учётные данные минимально необходимым доступом для их задачи, чтобы скомпрометированный ключ затрагивал только то, что требовала эта конкретная интеграция.

Управление секретом после аутентификации: хранение, ротация и отделение от конфигурации

Выбор правильного паттерна аутентификации устанавливает соединение, но поддержание его в безопасности — отдельная проблема. Упомянутая ранее утечка ключа MCP была не следствием неудачного выбора метода аутентификации, а следствием того, что учётные данные находились не в том месте и их нельзя было убрать после распространения. Три практики предотвращают это, и каждая устраняет конкретный способ утечки учётных данных.

Первая практика — это разделение: учётные данные никогда не перемещаются вместе с конфигурацией, которая на них ссылается. Конфигурационный файл содержит ссылку на переменную, а значение находится там, где файла нет. Именно это правило нарушил сбой с утёкшим ключом. Причина важности механическая: конфигурационные файлы коммитятся, распространяются и клонируются. Значение, записанное напрямую, перемещается вместе с каждой такой копией, а закоммиченное значение попадает в историю репозитория так, что перезапись его не удаляет. Если держать значение вне файла, файл остаётся безопасным для распространения.

Вторая практика — это куда уходит значение после того, как оно вынесено из файла. Для значения, живущего только на одной машине или в одном запуске пайплайна, достаточно переменной окружения, внедряемой в момент выполнения: CI-раннер задаёт её как секрет, конфигурация читает её по имени, и ничего не записывается на диск. Для значения, нужного нескольким сервисам или людям, лучше подходит хранилище секретов. Хранилище секретов — это управляемый сервис, который хранит учётные данные, возвращает их авторизованным вызывающим сторонам во время выполнения и записывает, кто что прочитал. Оно централизует значение так, что одна ротация обновляет всех потребителей сразу, и устраняет копии, накапливающиеся, когда каждый сервис хранит свои учётные данные в своём файле. Обращайтесь к переменной окружения, когда секрет локален и недолговечен, и к хранилищу секретов, когда секрет общий или должен подлежать аудиту.

Третья практика — это ротация: замена учётных данных новыми по расписанию и немедленно после любой предполагаемой утечки. Ротация — единственный подходящий ответ на утёкший ключ, потому что ключ, который был раскрыт, нельзя снова сделать секретным. Нужно выпустить новый. Именно поэтому паттерн встроенных учётных данных так дорого обходится: значение, встроенное в закоммиченный код, нельзя ротировать чисто, поскольку старое значение остаётся в истории, и каждый потребитель, жёстко привязанный к нему, ломается при изменении. Учётные данные, читаемые из хранилища секретов или переменной окружения, ротируются без изменения кода, который их использует, потому что код ссылается на значение по имени, а имя не меняется, когда меняется стоящее за ним значение.

Две привычки могут удешевить ротацию: ограничивайте каждые учётные данные минимально необходимым доступом для их задачи, чтобы утёкший ключ затрагивал только то, что требовала эта интеграция. Ведите учёт того, какие сервисы используют каждые учётные данные, чтобы ротация не выявляла их потребителей задним числом.

Сбой с утёкшим ключом ранее в модуле выявил ошибку: учётные данные, записанные напрямую в закоммиченный файл. Чтобы это предотвратить, применяйте эти три практики: разделение держит значение вне файла, хранилище секретов или переменная окружения дают значению дом, которым файл не делится, а ротация помогает с восстановлением только тогда, когда первые две практики соблюдены.

Что регулируемые отрасли добавляют поверх работающей аутентификации

Клиент из финансовой сферы или здравоохранения задаёт больше вопросов, чем просто «работает ли аутентификация?». Он спрашивает, где обрабатываются данные, как логируется доступ и может ли администратор заблокировать конфигурацию так, чтобы разработчик не мог изменить настройку аутентификации во время окна аудита.

Управляемая корпоративная конфигурация из предыдущих разделов отвечает на последний вопрос: конфигурация сервера, развёрнутая администратором и не переопределяемая отдельными пользователями, означает, что настройка аутентификации согласована по всей организации и не зависит от корректности файла настроек каждого разработчика.

Хуки аудита отвечают на вопрос логирования: хук PostToolUse, логирующий каждый вызов инструмента и его параметры в хранилище аудита, предоставляет запись, необходимую для проверки соответствия требованиям. Хук срабатывает детерминированно при каждом вызове, независимо от того, что решает модель, и лог — это то, что модель не может пропустить.

Резидентность данных отвечает на вопрос обработки: сервер, настроенный с HTTP-эндпоинтом в конкретном регионе, в сочетании с развёртыванием платформы, закрепляющим обработку за этим регионом, даёт проверяющему на соответствие требованиям проверяемый ответ о том, куда уходят данные. Именно поэтому требование к инфраструктуре и выбор платформы из предыдущей части модуля важны во время аудита, а не только во время сборки.

Модернизация кода: применение всего модуля к изменению унаследованного кода

Модернизация кода — полезный тестовый случай для всего, что охватывает этот модуль, потому что она концентрирует риски, для управления которыми был создан каждый инструмент. Масштабные изменения в незнакомой унаследованной кодовой базе несут высокий радиус поражения, непредсказуемые зависимости и ограниченную обратимость. Инструменты из этого модуля напрямую устраняют каждый из этих рисков, если применять их до начала работы. Цикл «исследование, план и код» — основной рабочий процесс для такого рода работы. Режим plan удерживает агента на фазе исследования только для чтения, пока вы формируете доверие к его изменениям. Вы можете просмотреть предлагаемые правки, определить всё, что затрагивает неожиданные пути, и отклонить их до того, как будет изменён хоть один файл. Хуки обеспечивают гарантии, предотвращающие правки определённых путей на самых чувствительных этапах. CLAUDE.md несёт соглашения для новых целевых паттернов, поэтому агент применяет их последовательно во всём объёме изменений, а не сползает обратно к устаревшим паттернам, которые читает в окружающем коде.

Ответственный подход к определению рамок для высокорисковой работы отвечает на три вопроса до начала сессии.

  • Каков радиус поражения, если что-то пойдёт не так: какие системы зависят от изменяемого кода и что сломается ниже по цепочке, если правка окажется неверной?
  • Как аудируются изменения: есть ли хук PostToolUse, логирующий каждый вызов инструмента, и удовлетворяет ли этот лог того, кому нужно проверить, чего касался агент?
  • Кто одобряет каждую фазу перед началом следующей? Режим plan обеспечивает границу между исследованием и выполнением, но само решение об одобрении — это то, что вы должны определить и задокументировать до начала работы.

Эти вопросы не специфичны для модернизации. Они применимы к любой высокорисковой агентной задаче. Модернизация кода отчётливо их проявляет, потому что масштаб велик, кодовая база незнакома, а цена ошибки высока.

Добавляет стоимость или сложность
Команды, не знакомые с потоками OAuth или управлением корпоративными секретами. Эти паттерны требуют координации с командами безопасности или ИТ в большинстве регулируемых организаций, и график должен это учитывать.

Настройка

Подключение OAuth работало сквозным образом в тестовой среде, поэтому перенос его в продакшен казался рутинным переключением. Команда упустила, что redirect URI OAuth регистрируются для каждого хоста и часто регулируются для каждой среды, поэтому успех в тестовой среде не означал, что продакшен-хост авторизован завершать процесс входа.

Разговор, выявивший пропущенный шаг

Следующий обмен репликами произошёл на разборе после развёртывания, когда интеграция MCP не сработала в продакшене. Интеграция прошла все тесты в тестовой среде.

Специалист по безопасности: «Каждая попытка входа в продакшене через подключение MCP завершается неудачей. Ошибка — несоответствие redirect URI. Где было зарегистрировано приложение OAuth?» Разработчик: «Я зарегистрировал его для staging.mycompany.com во время разработки. Мы перешли в продакшен на прошлой неделе. Подключение работало всё время в тестовой среде». Специалист по безопасности: «В этом и проблема. Провайдер OAuth принимает только те redirect URI, которые вы явно зарегистрировали, а production.mycompany.com нет в разрешённом списке. Каждая попытка входа проходит проверку, не проходит сопоставление URI и возвращается к экрану входа». Разработчик: «То есть мне просто нужно добавить продакшен-URI в регистрацию приложения?» Специалист по безопасности: «Да, и прежде чем это сделать, проверьте, должна ли регистрация вашего тестового приложения быть отдельной от продакшена. Большинство корпоративных клиентов требуют отдельных регистраций приложений OAuth для каждой среды как часть своей политики безопасности, так что использование одной и той же регистрации в разных средах — вторая проблема, на которую я бы указал».

Разработчик протестировал поток OAuth сквозным образом в тестовой среде и подтвердил, что он работает, а значит, сбой в продакшене не был дефектом кода. Вместо этого это был шаг конфигурации, применимый к каждому хосту и каждой среде, о необходимости которого для продакшена разработчик не знал.

На что обратить внимание

Redirect URI OAuth регистрируются для каждого хоста, поэтому работающее тестовое подключение OAuth не означает, что продакшен-подключение настроено. Прежде чем переносить любую MCP-интеграцию с аутентификацией OAuth в новую среду, добавьте redirect URI нового хоста в регистрацию приложения OAuth. Для регулируемых корпоративных клиентов проверьте, требуются ли отдельные регистрации приложений OAuth для тестовой среды и продакшена. Включите шаг регистрации в чек-лист развёртывания, чтобы его не обнаружили при первой попытке входа в продакшене.

Семь ключевых выводов

По одному выводу на раздел, связывающему модуль воедино.

1

Режим разрешений — это решение о риске, а не о скорости.

Claude Code даёт вам режимы от «запрашивать перед всем» до «не запрашивать ничего». Режим разрешений должен соответствовать профилю риска работы и среды, а не предпочтению меньшего числа запросов. Режим обхода на рабочей станции разработчика против живой кодовой базы убирает каждую точку контроля между агентом и вашими файлами. Правило deny для пути, который нельзя трогать, заданное на уровне проекта или предприятия, закрывает пробел, который один только режим не закрывает.

2

Обзор кода ИИ даёт вам набор находок для сортировки, а не вердикт для применения.

Доверяйте находкам, которые рецензент может доказать по диффу перед собой, например отсутствующей проверке на null или незакрытому ресурсу, и подтверждайте их по строкам, которые он цитирует. Относитесь к любому утверждению о поведении во время выполнения или другой системе как к гипотезе для проверки, потому что рецензент сделал это утверждение без доказательств, которые бы его подтвердили. Размещайте точку контроля человеком там, где находка превращается в действие, которое трудно отменить, и повышайте точность рецензента, давая ему соглашения, которые иначе пришлось бы угадывать.

3

Навык переносим, но «работает везде» — это то, что нужно проектировать намеренно.

Один и тот же SKILL.md может работать в Claude Code, в Messages API и через Agent SDK, но каждый из них загружает и изолирует его по-своему: обнаружение через файловую систему в Claude Code, бета-заголовки и контейнер выполнения кода в API, и settingSources в SDK. Навык, ограниченный чётким описанием и свободный от допущений о локальной среде, переносится без проблем; тот, что предполагает конкретный терминал, в котором был написан, — нет. В любой среде выполнения субагенты стартуют с чистого листа: они не загружают навыки автоматически заранее.

4

Устойчивый контекст требует правильного механизма для каждой задачи.

CLAUDE.md — это память проекта, сохраняющаяся в течение сессии, но она размывается с ростом размера. Файлы правил ограничивают указания местом их применения. Хуки обеспечивают гарантии детерминированно, а не вероятностно. Субагенты удерживают исследовательскую работу вне основного контекста. Каждый из этих четырёх механизмов решает свою задачу, поэтому попытка втиснуть их все в CLAUDE.md создаёт единый файл, который труднее поддерживать и легче игнорировать.

5

Настройка, пригодная для распространения, требует переносимых компонентов.

Плагин, ссылающийся на абсолютный путь к домашнему каталогу автора, установится на одной машине и не сработает на всех остальных. Навыки, хуки и компоненты плагина, которые будут распространяться, должны ссылаться на пути относительно корня проекта, а любое требование к переменной окружения должно быть задокументировано или проверено при установке. Тестируйте установку на чистой машине перед распространением.

6

Транспорт и область действия — независимые решения с зависимыми последствиями.

stdio — для серверов, работающих на вашей машине. HTTP — для всего, что размещено удалённо или доступно нескольким разработчикам. Локальная область делает сервер личным; область проекта распространяет его на репозиторий через .mcp.json. Сочетание должно соответствовать намерению развёртывания: общий командный сервер требует HTTP-транспорта и области проекта или предприятия. stdio-сервер в .mcp.json — это конфигурация, которая выглядит распространяемой, но не является таковой.

7

Корпоративная интеграция требует определения требований безопасности до развёртывания.

Регулируемый клиент спрашивает об идентичности, резидентности данных, логировании доступа и контроле конфигурации. Ответы дают: OAuth для сервисов с идентичностью пользователя, переменные окружения для служебных учётных данных, хуки PostToolUse для журналирования аудита и корпоративные управляемые настройки для блокировки конфигурации. Ни одно из этого не сложно реализовать, но всё это трудно добавить задним числом после того, как продакшен-развёртывание провалило проверку безопасности.

Ключевые термины этого модуля

По алфавиту. Нажмите на термин, чтобы развернуть его определение.

Claude Agent SDK

Программируемый интерфейс, предоставляющий доступ к тому же циклу агента, который Claude Code выполняет в терминале. Он позволяет разработчикам вызывать этот цикл из кода, задавать режим разрешений и доступные инструменты, а также выполнять задачи без интерактивной сессии. Та же модель разрешений и правила deny, что применяются в терминале, применяются и в SDK.

CLAUDE.md

Markdown-файл, размещённый в корне проекта Claude Code. Его содержимое добавляется в начало окна контекста при старте каждой сессии. Он содержит универсальные ограничения проекта, соглашения и команды, которые должны применяться безусловно во всех сессиях. Файлы, вырастающие свыше примерно 200–300 строк, рискуют размыть критически важные правила из-за веса содержимого.

Хук

Команда, привязанная к событию жизненного цикла в выполнении Claude Code (PreToolUse, PostToolUse, UserPromptSubmit, Stop). В отличие от инструкций в CLAUDE.md, хуки выполняются детерминированно в настроенном событии независимо от того, что решает модель. Хук PreToolUse может завершиться с кодом 2, чтобы заблокировать вызов инструмента до его выполнения.

MCP (Model Context Protocol)

Открытый уровень связи, позволяющий MCP-клиенту, такому как Claude Code, подключаться к MCP-серверу, предоставляющему инструменты, ресурсы и промпты. Протокол определяет, как клиент обнаруживает и вызывает инструменты сервера. Использование MCP выносит определение и поддержку инструментов из кода отдельного приложения в переиспользуемый сервер, к которому может подключиться любой MCP-клиент.

Транспорт MCP

Канал связи между MCP-клиентом и MCP-сервером. stdio запускает сервер как локальный подпроцесс на той же машине, что и клиент. HTTP подключается к удалённо размещённому серверу по сети. Выбор транспорта определяет, где может работать сервер и кто может к нему подключиться.

Режим разрешений

Настройка в Claude Code, контролирующая, как часто агент останавливается для запроса подтверждения перед выполнением вызовов инструментов. Режимы варьируются от default (запрос перед почти каждым действием) до режимов обхода (без запросов вообще). Правила deny переопределяют любой режим; правило deny на уровне корпоративных настроек не может быть обойдено никакой отдельной конфигурацией.

Плагин

Версионированный пакет компонентов Claude Code (навыки, хуки, субагенты и конфигурации MCP-серверов), распространяемый через маркетплейс. Установка плагина даёт получателю ту же настройку, что и у автора, в один шаг. Администраторы предприятия могут развёртывать плагины в масштабах организации через управляемые настройки.

Файл правил

Файл, ограничивающий указания конкретным путём или условием в Claude Code. В отличие от CLAUDE.md, который загружается в каждую сессию безусловно, файл правил активируется только тогда, когда Claude Code работает в каталоге, который он контролирует. Используется, чтобы держать специфичные для пути указания вне основного файла памяти проекта.

Субагент

Отдельный контекст выполнения, запускаемый Claude Code для обработки делегированной задачи. Субагент не наследует контекст основной беседы или накопленные файлы; он стартует с чистого листа, выполняет задачу и возвращает только резюме. Использование субагентов для исследовательской или разведывательной работы не даёт основному контексту сессии заполняться содержимым, которое не будет переиспользовано.
